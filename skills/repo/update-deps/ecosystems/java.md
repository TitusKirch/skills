# Java: Gradle and Maven

Read this when discovery finds `settings.gradle(.kts)`, `build.gradle(.kts)` or `pom.xml`, including below a Node workspace. Java often has no lockfile. Use the committed `gradlew` / `mvnw` from its build root; do not substitute a global version. Reporting tasks execute build code too, so the reference's verification isolation rules apply.

## Discover owners before candidates

For **Gradle**, read settings, `pluginManagement`, `dependencyResolutionManagement`, included projects, `includeBuild`, `buildSrc` / convention plugins, properties and imported version catalogs. `gradle/libs.versions.toml` is a declaration source, not a lockfile. Follow `version.ref` and bundles to their owner; include `[plugins]` and literal plugin versions in settings/build scripts. A convention build may import the parent catalog but still resolve its own dependencies. A catalog version is requested, not necessarily selected: platforms, constraints and conflict resolution can change the result. Inspect `dependencies` / `dependencyInsight` for the affected project and configuration.

For **Maven**, follow reactor `<modules>`, parents, properties, `dependencyManagement`, imported BOMs, `pluginManagement`, build plugins and active profiles. An external parent and a BOM are dependencies; this repo's own project/module release version is not an update target. Edit the owning property/parent declaration rather than adding child overrides. Use the same profiles/settings as CI; do not print repository credentials.

**Keep repositories and content filters.** Maven Central alone does not cover Paper, Velocity, CodeMC, PlaceholderAPI or JitPack coordinates. Resolve each artifact against its configured repository, including plugin repositories. Unreachable/private metadata is **unread**, naming the coordinate and host; never replace a repository to make the lookup succeed. Maven metadata can list candidates without installing a new updater.

## Versions and scope

- **Ordinary Java versions are declarations, not automatically policy pins.** A Gradle catalog `gson = "2.14.0"` or a Maven `<version>2.14.0</version>` is eligible within the requested range. Otherwise almost every Java update would be held by the npm exact-pin rule. Explicit holds, Gradle `strictly` / rejects, enforced platforms, verification metadata and documented compatibility constraints remain binding. A resolved lock entry alone is not an instruction never to update.
- **Filter candidates before editing.** Prefer stable patch/minor targets according to the artifact's version scheme. Do not reject a stable `.Final` solely for its suffix, or treat an RC, milestone, preview or `-SNAPSHOT` as a stable release. Two-component, calendar and platform versions need upstream evidence; an unclassifiable candidate is held, never guessed into a minor run. The conservative `0.x` rule still treats a change of the middle component as potentially breaking.
- **Platform-provided APIs need runtime compatibility.** `compileOnly` / Maven `provided` dependencies are still inventoried. Paper build tracks, Velocity APIs, Adventure and similar server-provided libraries must match the deployed platform, not just the highest metadata entry. Stay on an established snapshot/platform track only if the repo explicitly uses it and its policy permits it; report mutable snapshot resolution separately from a declaration change. Do not migrate server tracks or refresh all snapshots implicitly.
- **BOMs and coupled modules move together through their owner.** Verify the resolved family (for example JUnit Jupiter/Platform or Jackson); do not impose the same numeric version on artifacts whose release schemes differ. Local `files(...)` JARs and project dependencies are not Maven coordinates: follow an existing artifact manifest/updater if authorized, otherwise report the owner and hold them.
- **JDK and wrappers are separate toolchains.** Inventory Gradle Java toolchains, Maven compiler release/toolchains, CI JDK distribution/version, Docker runtime, `.java-version` / `.tool-versions` and wrapper properties. Dependency scope alone does not authorize a Java language-level or Gradle/Maven wrapper upgrade. If authorized, check the JDK/build-tool compatibility matrix, preserve checksum verification and use the wrapper's update procedure. Do not install a host JDK or bypass checksums to complete a package update.

## Plan, write and verify

Use an existing repository update/report task first. A configured Gradle `dependencyUpdates` task is a report, not a built-in Gradle command or an approved candidate filter. For Maven, an already configured Versions plugin can run `versions:display-dependency-updates`, `versions:display-plugin-updates` and `versions:display-property-updates`; its reports still need range, stability and owner filtering. Do not add plugins just to report updates or run bulk `use-latest-versions` / `use-latest-releases` blindly. If no updater is available, resolve metadata and edit the specific catalog keys, properties or declarations in the approved plan.

If Gradle locking is enabled, regenerate affected locks through tasks resolving the relevant configurations, using scoped `--update-locks group:artifact` where appropriate. A bare root `dependencies` task need not resolve subprojects or included builds. `--write-locks` needs the same configuration coverage; never invent a shared root lock or hand-edit locks. Do not enable locking as an incidental update. Preserve dependency verification: inspect new artifacts against trusted upstream checksums/signatures before accepting generated verification metadata. Do not disable verification or blindly trust whatever was downloaded. Maven normally has no lockfile.

Run the repository gate and its affected Java build coverage (`./gradlew check`, included-build checks where omitted, or `./mvnw verify`, using the repo's actual tasks/profiles). Compilation alone does not establish server API compatibility; include existing distribution/runtime checks. A missing JDK, unresolved private artifact or skipped integration task is **unverified**. Use the repo's configured advisory scanner, such as OWASP Dependency-Check; if absent, report **unavailable**. pnpm's age gate does not protect Maven artifacts: preserve any Java-specific repository policy and otherwise report the age gate **not applicable**.

## Example: Java inside a mixed monorepo

A pnpm/Turbo repo can have `packages/minecraft/package.json` running `./gradlew check`, with libraries and Paper/Velocity plugins in Gradle settings, a `build-logic` included build importing `../gradle/libs.versions.toml`, a Shadow plugin dependency there, and a literal Foojay resolver plugin in settings. Inventory all those owners once. The root pnpm lock owns Node tooling; the catalog owns Java declarations; build logic has separate resolution. The JDK toolchain and Gradle wrapper get separate held/authorized rows. A PHP service's Composer lock and a Rust tool's Cargo lock remain separate roots. This topology does not grant permission to edit server image pins or externally supplied plugin JARs.
