# Tracker — GitLab (`glab`)

The **GitLab** branch of `refine-issue` — reached when `work.tracker` (falling back to `issue.tracker`) resolves to `gitlab`. Everything a run needs whatever its tracker stays in `REFERENCE.md`.

The mechanics below are `trackers/github.md`'s in GitLab's spelling; anything not named here is unchanged.

**Every call runs against the host this repo resolves, never `gitlab.com` by assumption.** The ladder is stated once, as **The forge and its host** — the `issue` skill's `REFERENCE.md` carries it, and the work loop's two units carry the same copy: the root `forgeHost` key, else the host in the `origin` remote, else whatever `glab` is already configured for. Pass the result as `GITLAB_HOST` and let the CLI keep the credentials. Self-hosted is the **normal** GitLab deployment rather than the exception, so a run that skips the ladder either reads a stranger's backlog or reports an authentication failure that is really a wrong host — and on a self-hosted instance those two look identical in the error. Name the host in the report wherever it is not `gitlab.com`.

- **Read** — `glab issue view <n> --output json --comments` for the brief. There is no field selector — `glab` returns the whole issue rather than `gh`'s `--json title,body,…` — so the fields are picked out locally. `--output json` matters as much on this call as on the list one: the default rendering is built for a human to look at, and a body parsed back out of it silently picks up a wrapped line. The notes are part of the brief, judged by **Author authority** in `REFERENCE.md` — whose GitLab tier is an access level of at least **Developer (30)**, read from `projects/:id/members/all/:user_id` with inheritance included, since on a group-owned project most maintainers hold their access through the group rather than on the project itself.
- **Candidates** — the negative label search in **Finding the candidates** (`REFERENCE.md`), with the exclusion applied **locally**: one `glab issue list --output json` and drop every issue whose `labels` already name a lifecycle string. GitLab's list has no OR-of-negations qualifier answering to `gh`'s `--search '-label:… -label:…'`, and the entries carry their labels anyway, so filtering in the shell costs nothing and needs no bet on how a negated flag combines its arguments — the trap the implement loop's own GitLab recipe names for the positive filter (**`glab` ANDs a comma-separated `--label`** where `gh`'s search qualifier ORs it) is the same trap read backwards.
- **Duplicates** — `glab issue list --search '<the issue’s key terms>' --output json`, which matches title and description. There is no counterpart to `gh search issues`: the search is a **flag on the list call**, so it is scoped to the project the resolved host and remote already point at rather than by an `--repo` argument, and a cross-project sweep is not something this skill reaches for.
- **Already solved** — the `git log --since=` half of **Already solved** (`REFERENCE.md`) is local git and runs unchanged. The merged-request half is `glab mr list --merged --output json` with the date bound applied locally over each entry's `merged_at`, since `glab` has no `merged:><since>` search qualifier; where the bound matters more than the page size, `glab api 'projects/:id/merge_requests?state=merged&updated_after=<since>'` applies it server-side instead. Speak the forge's own vocabulary in what the report says — a **merge request**, not a pull request.
- **Write** — `glab issue update <n> --description "$(cat <tmp>)"`, once, after confirmation. **`glab` has no `--body-file`**, so a multi-line markdown body goes through a temp file and command substitution, exactly as the `issue` skill's driver does on create. The write carries **no label flag**, and that is worth restating on this tracker rather than inheriting quietly: `glab issue update` is the very command the lifecycle flip uses (`--label` / `--unlabel`, both rideable in the same call as `--description`), so the write this skill must not make sits one flag away from the one it does. `REFERENCE.md`'s "never together with a label change" is the whole guard here.
- **The label stays for the human** — `glab issue update <n> --label "<ready>" --unlabel "<needsTriage>"` is printed, never run. `--unlabel` is `gh`'s `--remove-label` and both flags ride in one call, so the report's one command stays one command (**Report output** in `REFERENCE.md`); the second flag only where the marker is configured and the issue carries it.

## The label shape is inherited, not settled here

This recipe states **no label-shape convention of its own**. The lifecycle is flat, exactly as `work-implement`'s GitLab recipe already states it, and the lifecycle names come from `work.labels.*` verbatim — as they do on every tracker. A repo spelling its lifecycle with GitLab's scoped syntax (`ai::ready`) says so in `work.labels.*`, and every skill reads that string the same way; nothing here has to know which of the two shapes it is holding.

That the question does not arise at all is a property of **this** skill rather than of the tracker: `refine-issue` applies no lifecycle label — it prints the command a human runs — so there is no write on which a shape would have to be chosen. What the run does need from the catalog is resolution, and there GitLab's scoping is real: a label may be the **project's** or the **group's**, a group label applies by name exactly like a project one and reads back among the issue's labels either way, so resolve against both before reporting a label as unresolvable.
