# work-implement / work-implement-queue — Design

The decision record behind the work skills. The "why"; `REFERENCE.md` holds the "how". Captured from the design sessions so the rationale survives.

## Core principle

**The queue is the tracker; the worker is stateless.** State lives in the issue's lifecycle label, not the agent. Each run reads tracker + git fresh, so runs are **resumable** (a crash continues, not restarts) and **idempotent** (a repeat is safe). Every decision below serves this.

## Four skills, two loops

| Skill                        | Role                                                                              | Invocation                       |
| :--------------------------- | :-------------------------------------------------------------------------------- | :------------------------------- |
| [`work-implement`](SKILL.md) | The unit — one issue → one reviewable PR. A state machine over a single issue.    | model-invocable                  |
| `work-implement-queue`       | The drain — select, prioritise, work the queue; delegates each to a fresh worker. | user-invoked, looped via `/loop` |

The workflow is **two loops**, each a unit + a drain: **implement** (`work-implement` / `work-implement-queue`) builds and pushes; **review** (`work-review` / `work-review-queue`) reviews the pushed work as a **different** agent. The units are model-invocable so a drain — or an ad-hoc `/work-implement 42` / `/work-review 42` — can reach them; the queues are user-invoked so a heavy autonomous drain never fires by accident, and `/loop` is the temporal layer. **Why a separate review loop:** an independent reviewer with fresh context carries no "it works because I wrote it" bias, and the split lets the review drain run on its own cadence (even a different machine) from implementation. The two loops hand off through two labels — `reviewRequested` (implement → review) and `changes-requested` (review → implement) — and use **separate single-flight locks**, so they run concurrently.

The lifecycle is **symmetric**: each loop has a **waiting** state and an **in-flight** state — `ready → working → review requested → reviewing → done`, with `changes requested` looping back to `working`. `ai: working` is the implement loop's lease; `ai: reviewing` is the review loop's, added so the review side has the same tracker-global claim the implement side has always had — on a tracker that is a server, which the `local` driver is not (there the store sits inside the checkout, so the lease reaches no further than the lock; `work-review`'s REFERENCE states it and recommends leaving the lease off).

## Key decisions

- **Concurrency is impossible by construction**, not locked — one live worker per tree, strict sequential `await`, plus a per-checkout single-flight lock (a specified path in the git common dir, acquired with an atomic `mkdir`, evicted by owner metadata rather than a raw age TTL). Its mutual exclusion holds **within one checkout**, not across clones — a boundary stated plainly rather than papered over, with the reconcile's assignee guard, not the lock, protecting a second clone's live work. Git's `index.lock` is only a backstop.
- **Lease before work** — flip `ready → working` + assign _before_ implementing. The race-breaker for two consumers grabbing one issue.
- **The review loop leases too (`ai: reviewing`), mirroring `ai: working`.** The single-flight lock only proves no live worker holds an issue **in this checkout** — a second clone's worker holds its own lock, invisible here. The implement loop closes that gap with the `working` label plus the assignee guard; the review loop had the lock but no label, so two clones draining `work-review-queue` (CI and a laptop, say) both selected the same `reviewRequested` issues and reviewed them twice — and worse, the verdicts _compete_ (A sets `done`, B sets `changes requested`, last-write-wins). The fix is the same tracker-side claim: a `reviewing` lease both clones can see. **Justified by mutual exclusion, not crash recovery** — `working` earns its keep because there is a pushed artifact whose existence the reconcile queries; a review writes nothing, so a crash mid-review costs only tokens. **Opt-in** (`labels.reviewing` defaults to _off_): a single-clone setup has no second drain to exclude, so the lease stays off until a repo turns it on, leaving every existing adopter's behaviour unchanged. Rejected: **a cross-clone lock** — the lock lives in the git common dir and cannot observe another clone by construction; only a tracker-side label is visible to both.
- **The label is operative for eligibility; the body governs scope.** Both are live and can disagree — a creation-time "not ready yet" note outlives the label a human flipped days later, and a run that trusts the older text hands back a decision the human already made. The label is the queue's contract and the deliberate act, so it decides _whether_ to work an issue; the body decides _what_ the work is. A contradiction is **surfaced as a warning**, never a silent self-block: flagging it lets the human fix the wrong side, whereas blocking on it buries a live decision under stale prose. Rejected: **arbitrating by timestamp** ("newer human act wins", via the tracker's timeline/history API) — an operative label never asks which side is newer, so the comparison costs an API call per issue to answer a question the rule does not pose, and re-opens as a race the thing the rule settles by construction.
- **One PR per issue by default** (`branch: worktree`) — independent, reviewable, revertable; revisions stay isolated. The branch base is always the clean `pr.base`.
- **Branch strategy is two independent knobs** — `branch` (`worktree` | `branch:<name>`) × `parallel` (bool). Worktrees are the _mechanism_ of `parallel`, not a mode; a shared `branch:<name>` + `parallel` is made safe by **serialized integration** (so `branch:dev` + `parallel` works).
- **Relations are read under both strategies; only the _response_ differs — order on a shared branch, defer in worktrees.** Under `branch:<name>` the branch accumulates, so working prerequisites first is the entire mechanism — topological order, priority as tiebreak, cap applied after. Under `worktree` nothing accumulates, so no order the run picks discharges an edge; the response is to **decline to select** the dependent and report it deferred. _Supersedes the original "under `worktree` the `ready` gate governs": that gate is a human remembering not to mark a dependent issue `ready` before its prerequisite merges, and `worktree` is the schema default, so the common case was a modelled dependency the tool read and ignored in silence — the same class of failure as a label the tracker lacks returning exit 0._ Rejected: **warning but working the issue anyway** — the run's whole output is a PR built on a base missing its premise, so a warning would annotate wasted work rather than prevent it. Rejected: **`blocked`** — that label is a verdict about the work needing a human to clear it, whereas an unlanded prerequisite clears itself; deferring writes no label at all, so a later run picks the issue up unaided. Rejected: **gating on `parent` as well as `blockedBy`** — a parent epic normally closes _after_ its children, so it would stall every sub-issue of every open epic; `parent` stays an ordering input only. Stacking is still deferred: declining to select needs none of its machinery.
- **An edge is satisfied by a landed prerequisite, not by an accepted one.** `done` means [AI-accepted, not shipped](REFERENCE.md#terminal-done), and with a non-default `pr.base` GitHub's `Closes #<n>` never fires — so an accepted issue stays **open** forever and a closed-only test would defer its dependents forever. The test is therefore closed **or** a PR merged into `pr.base`, read with the same `closedByPullRequestsReferences` query the reconcile already runs. Rejected: **treating `labels.done` as landed** — it is precisely the state the rest of this design insists is not shipped.
- **"Not at the same time" is its own relation, read as a mutex — not a `blockedBy` edge.** Dependency ordering knows only edges meaning "A must land before B", and the dominant case in refactoring work is neither: A and B touch the same file, either order is fine, they simply must not run **simultaneously**. Forcing that into `blockedBy` invents an order nobody declared and gates B behind A permanently, so the ordering graph fills with edges that mean nothing. The constraint therefore gets an **order-free** relation of its own, and the only thing it does is **split a concurrent batch into waves within the same run** — no label written, no issue deferred, priority still choosing which goes first. **The carrier differs per tracker because the trackers differ:** Linear has a native order-free `related` relation; GitHub, checked against the API, has only `blocked_by`/`blocking` and sub-issues — all ordered — so its carrier is the label convention **`mutex: <group>`**. A label is visible in the UI where the human declaring the collision already works, filterable with a plain `gh issue list --label`, and free to read (labels already ride along on the selection query). Rejected: **a body convention** — invisible in every list view, and the queue would have to parse prose to find it. Rejected: **a config-declared group** — it puts issue numbers into a committed file that goes stale the moment one closes, and a collision is a property of two issues, not of the repo. Rejected: **detecting path overlap automatically** — that means predicting each issue's diff before implementing it, already rejected for the same reason when the ordering rules were written; this decision is about **declaration**, where the human already knows the two collide. Rejected: **leaving it to a human not to mark both `ai: ready` at once** — that is the status quo, and it is the same class of silent failure as a modelled dependency the tool reads and ignores. Rejected: **connected components of Linear's `related` graph** — the relation is pairwise and not transitive, so components would serialize pairs no human joined; a GitHub `mutex:` label _is_ an equivalence class by construction, and the two shapes are allowed to differ. Rejected: **making the `mutex: ` prefix configurable** — unlike a lifecycle label there is no existing repo vocabulary to accommodate and nothing stalls when the convention is unused: no label simply means no mutex.
- **A rebase conflict on a shared branch resolves out of the issues, or stops.** `push → rebase → retry` answers the **race** and cannot answer the **conflict** — a retried rebase collides again — so the one strategy where an agent would actually have to resolve (`branch:<name>`) was the one with no rule, which is undefined behaviour rather than a conservative default. The rule drives `resolving-merge-conflicts` for the **method** — recover each side's intent from its **primary sources** instead of the hunks — while the **decision to stop stays with this skill**: where both intents do not carry, `blocked`. That deliberately deviates from the called skill's "always resolve; never `--abort`", because on a shared branch a mis-resolution lands on the branch itself and the review loop then sees a merged result rather than a question. **The caller hands the sources in**: under serialized integration the other side is a sibling issue of the same drain, whose number and body the run already holds — better than the commit-message archaeology the skill assumes, and unreachable from inside it. **Scope is `branch:<name>` at either `parallel` setting**, since a second clone, a human or a merged dependency PR produces the same stop in a sequential run; `worktree` stays out, its conflicts surfacing at PR merge, outside the run entirely. The resolved tree is **re-verified before the push** — it is not the tree the verify step passed, and a commit pushed straight to a shared branch opens no PR for a pull-request-triggered CI to run on; that `work-review` re-establishes green against the pushed head anyway makes the re-run a cheap second gate rather than the only one. Rejected: **blocking on any conflict** — safe, and it would at least be _stated_, but it discards the resolutions the two issue bodies make obvious. Rejected: **writing our own resolution rules into this skill** — duplicates a small, well-scoped skill and drifts from it. Rejected: **serializing harder** so two issues never touch the same paths — path overlap is not a declared relation the way a prerequisite is, so it would mean predicting each issue's diff before implementing it.
- **An optional call is declared once, referenced at each site.** Three steps hand work to a separate skill that may not be installed (`atomic-commit`, `pull-request`, `resolving-merge-conflicts`), and the house rule is that a call states whether it is required or optional and what happens when it is absent. Stating that per site invites three subtly different fallbacks; stating it once, with a table of site → skill → fallback, keeps them one rule with three rows, and gives the two riders — the caller keeps its own authority over outcomes, and a called skill's human-facing step simply does not run in an unattended drain — a single home instead of a per-site repetition.
- **`done` = AI-reviewed and accepted, not the merge.** Native tracker automation cannot be the terminal signal — GitHub's `Closes #<n>` and Linear's integration fire only on a **default-branch** merge, so every repo whose `pr.base` is an integration branch had an **unreachable terminal state**. So `reviewRequested` is a real waiting state, but the verdict comes from an **independent AI reviewer** (the review loop): approve → `done`, changes → `changes-requested`, escalate → `needs human` (where a human's word resolves it). `done` means **accepted**, not merged — shipping is the rollup merge's business (`release`). _Supersedes the original "the human signs off in the same session" model: a human-in-session is too slow and too trusting for an autonomous drain, whereas an adversarial second agent scales and catches more; the human is now the escalation path (`needs human`), not the default gate._
- **Each drain's first step is its own reconcile, not a new trigger.** Drains run anyway, so orphans get swept without a dedicated trigger. There are two: the **implement** drain reclaims `working` orphans (crash before push → `ready`, after push → `reviewRequested`); the **review** drain closes out out-of-band human actions on a PR (merged → `done`, closed-unmerged → `blocked`) and, when the `reviewing` lease is on, reclaims `reviewing` orphans → `review requested`. **Closed-unmerged → `blocked`** because only the human knows whether it means rework, superseded, or abandoned — the side-exit's exact purpose. **A `reviewing` orphan always returns to `review requested`** — unlike a `working` orphan there is no before/after-push split to reason about, because a review pushes no artifact; the same assignee/age guard still applies, so a live review in another clone is never killed.
- **AI-accepted and shipped are two states, so Linear gets two.** The verdict wrote `states.done`, which every team reads as _shipped_ — while the work sat on `pr.base`, unmerged and unreleased, with Linear's integration firing only on a **default-branch** merge and therefore never correcting it. The label was right and the board was wrong. So the accept verdict now writes **`states.accepted`** (a `Ready for release` column), and **`states.done`** becomes the terminal shipped state that **neither loop writes** — Linear's own integration where `pr.base` _is_ the default branch, otherwise the `release` skill at the promotion edge that lands there. Rejected: **re-pointing `states.done` at the accepted state and adding `states.shipped`** — the option that "breaks fewer configs", which on inspection is the same thing as leaving every existing config wrong: their `done: "Done"` would keep being written at accept time, silently, which is the bug. The chosen split fails the other way — an unmigrated config leaves the state untouched (the existing "unmapped step" rule) rather than claiming a ship. Rejected: **renaming the `done` label** — `ai: done` already means AI-accepted, correctly; renaming it churns every repo's config and tracker for no gain, so the step key and the state key are allowed to differ exactly where their meanings do. Rejected: **documenting the meaning harder** — `done` is not merged was already stated one section above the mapping and did not stop it; prose does not fix a board.
- **A mapped Linear state is best-effort, and the contract says so instead of defending it.** The write itself was never the bug: each step writes its state atomically with the label, once. But **Linear's own GitHub integration writes the same field on any event on the linked PR** — a routine bot comment was enough in the observed run — within seconds, and **label-blind**: one drain saw five issues on four different lifecycle labels (`review requested`, `reviewing`, `needs human`, `done`) all moved to one state, `needs human` among them, which is mapped to nothing on purpose. Neither reconcile brings them back: neither sweep inspects a workflow state, so neither detects a drifted one, let alone repairs it. So `work.linear.states` is now documented as a **best-effort write, not a state these skills maintain**, with the three places a foreign write costs something silently named — `statuses` in the selection query in **both** directions (a state outside it stalls an eligible issue; a state inside it grants eligibility nobody gave, which only a positive label gate absorbs, and `labels.ready: false` leaves `statuses` as the sole positive gate) and `states.accepted` as the `release` skill's ship filter — and the repo pointed at the levers that work: turning the integration's PR state automation off (which removes the _automated_ writer, never the human one, so `statuses` stays generous regardless), widening `statuses` **where a label gate still exists**, or leaving `states` unmapped and driving by label alone (which buys the board's honesty and nothing about the queue — `statuses` is a separate, schema-required key the selection query reads either way, so under `labels.ready: false` that answer has to be paired with silencing the integration). Rejected: **a state-reconcile sweep** re-asserting each label's mapped state at drain time — the competing writer is event-driven and a sweep is not, so it would converge until the next PR comment and flap after; to be useful it would have to write issues neither loop owns (`needs human`, `done`), widening the loops' write scope; and it cannot tell the integration's write from a human's deliberate board move, so it would revert both. Rejected: **re-writing after the event** — nothing in a skill observes PR events, and racing an integration that fires in seconds is a race, not a fix. Rejected: **dropping `states` altogether** — the mapping is right for the minutes it holds, and for a repo that silences the integration it holds indefinitely; the defect was the silent promise, not the feature.
- **`review-after-land` on a shared branch.** Under `branch:<name>` (e.g. `branch:dev`) the commit lands on the branch **before** review — there is no PR gate. The issue is still not `done` until the review loop passes it; a `changes-requested` verdict is fixed **forward** (more commits), never reverted, and the reviewer diffs the issue's **own commit range**. Transiently-unreviewed code on an integration branch is acceptable because it is not released until the rollup PR, where the human code review also happens. _Supersedes the original "no PR → straight to `done`" rule, which skipped per-issue review entirely — the review gate now applies to every issue, PR or not._
- **Push is the reviewability boundary.** `working` covers "committed locally, not yet pushed"; only the push flips to `reviewRequested`, because a reviewer (a different agent, possibly a different machine) can only judge what is on the remote. A crash before the push is a `working` orphan the implement reconcile reclaims — to `ready` (no pushed artifact → redo) or to `reviewRequested` (already pushed → finish the hand-off). Rejected: a dedicated "done-not-pushed" state — it is unreachable local work a label cannot make reachable, so it is an orphan case, not a resting state.
- **Round count from tracker events, not a stored counter.** One round = one `working → reviewRequested` transition = one `reviewRequested` label-add; the reviewer counts those events (`work.review.maxRounds`, default 3) before choosing `changes-requested` vs escalating to `needs human`. Rejected: a hand-maintained comment counter — editable/deletable, and bookkeeping an agent must not lose; events are tamper-resistant and need no discipline. **Side effect of the `reviewing` reclaim:** flipping a `reviewing` orphan back to `reviewRequested` re-adds a `reviewRequested` label-add, over-counting that issue's rounds by one — the same quirk today's crash-after-push `working → reviewRequested` reclaim already has. It is left as a documented caveat, not a mechanism: over-counting errs toward escalating to `needs human` **earlier**, which is the safe direction the cap exists to guarantee, and a real fix (distinguishing reclaim re-adds from genuine hand-offs) would add a second, driftable signal for no safety gain.
- **Escalation to `needs human` is reviewer judgment, not a config paths-list.** The reviewer leans on existing repo signals — CODEOWNERS, branch protection, ambiguous intent, size/risk — rather than a `work.review` allowlist that would be a second, driftable source of truth. Only `maxRounds` is a config knob.
- **The checks are a gate; the discipline is a skill we drive, not one we write.** Step 7 says whether the tree still passes — nothing about how the code got written, so an unattended loop can pass it with tests that hold by construction (mocked collaborators, assertions that recompute the expected value the way the code does, tests written afterwards against the shape already built), and the review loop then reads a green run as evidence. `tdd` already carries the missing half — red before green, vertical slices, seams over internals, the anti-patterns named — and is **model-invocable**, so a skill can actually drive it. So step 6 drives it as an **optional** call in the same shape as `issue` → `grilling`: present → run the loop, absent → implement exactly as today. **The issue body substitutes for `tdd`'s confirm-the-seams step** — unattended there is nobody to ask, and `ai: ready` already made the body a human's approval of a scoped issue, so its requirements and acceptance criteria _are_ the agreed seams. **Where tests cannot reach, none of this applies:** a prose-only change drives `tdd` not at all, deliberately not a block, since most changes in a skills repo are markdown. **Red belongs to the step, not to the lifecycle** — the loop's failing tests live inside step 6, step 7 stays the only gate, so nothing about the cycle is carried as state and the worker stays stateless. Rejected: **writing our own test discipline into the skill** — no external dependency, but it duplicates a well-developed skill and drifts from it. Rejected: **leaving it to the checks plus the review loop** — that is today, and it treats a green run as evidence of quality rather than as a floor. Rejected: **letting the run choose its own seams** when the body yields none — seams picked after the implementation exists land exactly where the implementation is, which is the failure mode being fixed, so a code change with no seams in the body takes the `blocked` side-exit instead. Rejected: **binding `work-review` to the pass** — what was driven is recorded for the reviewer, but the verdict still rests on the diff against the requirements; judging tests _as_ evidence is the review loop's own question.
- **Verify before the PR** so `reviewRequested` is honest; red-and-unfixable → `blocked`. `blocked` continues the drain — only a skill error stops it.
- **A drain names its queue's state, so the loop rule lives in the skill instead of the prompt.** Both queues are written to be looped, and from outside every ending looks alike: a cap-ended drain with five issues left, a drain whose input the counterpart loop is still producing, and a genuinely empty one. The rule separating them therefore lived in whoever typed the `/loop` prompt — retyped each run and silently absent when it was not — whose failure mode is the **false finish**: the implement loop stops on its own empty queue while the review loop is mid-issue and about to hand an issue back. So the final step names one of `work remaining` / `backpressure` / `quiescent` and what a driver should do with it. **The wait condition is narrower than "something is still open"** — `done`, `blocked` and `needs human` are terminal and produce no input — and **cap-reached is not queue-empty**, the easiest of the three to conflate. **The bound is the counterpart's lock heartbeat**, which the lock already re-stamps per iteration: it answers "is anyone producing my input?" and separates **slow** from **dead**. **The tracker is read first and the lock only sharpens it** — an absent lock is deliberately _not_ a stop on its own, because the lock is checkout-local and its absence is equally the counterpart sitting in the gap between two cap-ended runs or running on another host; stopping there re-creates the very false finish, so the fallback is the waited-on issues' `updatedAt` — coarse (it moves only on real tracker writes) but visible from every host and already there. That makes **cross-host supported but degraded**, stated in the prose rather than left to be discovered: its window has to be generous, hours like the stale window, because a long iteration writes nothing to the tracker meanwhile. A real cross-host heartbeat needs shared storage, which the lock spec puts outside skill prose, and that boundary stays. **Re-querying the tracker precedes any wait** — work that became eligible during the last issue already exists — and the empty result that immediately follows a finished issue is therefore expected, never evidence of a quiet queue; only a check after a **wait** is that. Rejected: **a fixed round count** — a large issue sits in `working` for an hour with no label moving, and a count aborts on it. Rejected: **reusing the lock's stale window as the poll interval** — that window is crash detection, deliberately hours, and polling that rarely makes the loop useless; two jobs, two numbers. Rejected: **a supervisor skill driving both drains** — it re-couples what the two-loop split deliberately separated and does not answer the question, replacing `/loop /work-implement-queue` with `/loop /work-queue`; if the two sessions are ever wanted as one it would sit **on top of** this state report, not instead of it. The report stays **prose naming a state**, never a driver API call, so `/loop`, cron and a human all read the same thing and no skill takes on a client-specific dependency.
- **The gate installs first wherever it is not in the working tree**, which is why this skill carries the **isolated** check-command block and not the base one. `parallel: true` runs each worker in its own worktree, and a worktree holds **tracked files only** — nothing gitignored, so no `node_modules`, no `vendor`, however installed the tree next door is. A gate run there resolves against `PATH`: falsely green where the tooling happens to be global, red where it is not, and in neither case testing the versions the branch pins — which would make `reviewRequested` exactly the lie the previous point exists to prevent. That the commits are the run's _own_ changes nothing; emptiness follows from the tree being new. Rejected: **carrying the base block and gating the install on `parallel`** — the block's own heading already scopes the install to a tree that is not the working tree, so the isolated body is inert on the sequential path anyway, and a config-keyed roster would have to be kept in step with a knob the block cannot read. Also rejected: **the skill pre-seeding a worktree** by copying or linking the installed directories — it hides a dependency state the gate is supposed to establish, and one `node_modules` shared by two live workers is one install either can leave wrong for the other. The **cost is real and is documented rather than optimised away**: each concurrent worker pays a full install, which on a large repo can outlast the implementation it gates — the argument for `work.concurrency` (next point), not for a quietly shared cache.
- **Concurrency is its own knob, not a second meaning for `cap`.** `cap` bounds the **run** (throughput, "work up to 20 issues"); how many workers may be alive **at once** (disk, CPU, tracker rate limits, and under `worktree` + `parallel` a whole worktree and a full install each) is a different number that moves for different reasons. While `cap` carried both, the only way to run gently was to run briefly — the machine's ceiling forced extra drain invocations, each re-paying the reconcile and the queue build. So `work.concurrency` bounds the moment, **defaults to `cap`** (a config that omits it behaves exactly as before), never raises it (the effective width is the lower of the two), and is inert under `parallel: false`, where one worker at a time is the construction. Rejected: **reusing `cap` and documenting the double meaning** — cheaper, but it leaves two limits welded together that a machine change and a backlog change each want to move on their own. Rejected: **deriving it** from core count or free disk — the binding constraint is repo-specific (install size, API rate limit, a laptop shared with its user) and a guess that reads plausible is worse than a number the repo states.
- **"Unfixable" is a verdict with a procedure behind it, not a feel.** Of the three limbs of the block clause, _spec ambiguous_ and _a genuine human decision_ are judgements a run can actually make; **unfixable** was a verdict with nothing stated as having to be attempted first — and it is the **cheapest legitimate exit from a loop**, because it ends a run without failing it. Nothing separated _"I built a reproduction and the cause sits outside this issue's scope"_ from _"I guessed twice and moved on"_, and the issue comment recorded the conclusion either way. So `diagnosing-bugs` is driven as an **optional call** at the two moments that are bug judgements — step 6 where the issue **is** a bug (the work is the diagnosis) and step 7's **red** branch — in the same shape `issue` → `grilling` already uses: invoke when installed, behave exactly as today when absent. **The join is that skill's own stop rule**: it refuses to speculate when no feedback loop can be constructed and says so, listing what it tried. That _is_ `blocked` — so the call does not make `blocked` rarer, it makes it **checkable**, which is why what the comment carries changes from the conclusion to the **attempt**. Rejected: **writing our own diagnosis discipline into this skill** — no external dependency, but it duplicates a well-developed skill and drifts from it. Rejected: **leaving it** — that treats "unfixable" as a judgement an unattended run is qualified to make unaided, which is precisely what such a run is worst at. Rejected: **driving it on all three limbs** — a reproduction answers neither an ambiguous spec nor a human call, so those keep blocking immediately. **The last rung is documented as gone, not improvised around**: the skill's human-in-the-loop technique needs a person at a terminal, so unattended it is unavailable rather than merely expensive, and an exhausted ladder whose final rung was never reachable is a stated reason to block. Left to the **review** skill: whether a reviewer should re-derive a `blocked` claim the way `work-review` already re-derives green rather than inheriting the claim — consistent in posture, but a change to a different skill.
- **The loops' round-by-round output belongs on the artefact, not on the requirement** (`work.feedback`). Three review rounds turned an issue into an agent log — verdicts, changes-requested rationale, re-work notes — burying what the issue actually asks for under the record of how the loop got there. So the destination is configured with **both modes real**: `pr` puts it on the pull request and leaves the issue its requirement, its label and a link to the thread; `issue` keeps today's behaviour for a loop that opens no PR. The **default is derived from `work.branch`**, not a fourth knob — `worktree` opens PRs, so `pr`; `branch:<name>` opens none, so `issue` — which means the repo running `branch:dev` needs no config change at all. **No pull request in `pr` mode falls back to the issue** rather than refusing: a `blocked` exit happens _before_ the push, so refusing would drop exactly the output the run existed to produce, and a destination is a routing preference, never a gate. **Only writing is routed** — a re-work and a re-review read both places, because the mode may have changed and **old comments are not migrated**. Rejected: **always post to the PR** — silently drops all feedback in the mode this repo itself runs. Rejected: **always post to the issue** — the log this exists to end. Rejected: **post to both** — doubles the noise the change exists to cut. Rejected: **Linear's own diff threads as the `pr` destination** — the loop's artefact is a GitHub PR even for a Linear-tracked repo, so the thread already exists and Linear's is a second, empty one.
- **In `pr` mode the plain comment is the primitive and the formal review an optional upgrade**, because GitHub refuses `gh pr review --request-changes` / `--approve` on a pull request the caller authored — and where the implement and review loops run as **one identity**, which is the ordinary single-owner setup, that is _every_ PR the loop produces. Prescribing the review call as the way `changes-requested` reaches the implement loop would therefore fail the loop's most load-bearing verdict by construction, in the very mode `worktree` defaults to. `gh pr comment` succeeds on one's own PR, lands in the same thread, and is all `feedback: pr` ever promised; the review call is reached for only where the reviewer identity demonstrably differs (a separate bot token, a second account, a multi-maintainer repo), and its refusal is a **second documented fallback** — post the same body as a comment, name it in the run report — beside the no-PR one. Rejected: **escalating to `needs human` on the refusal** — it conflates a rejected _call_ with an unreachable _verdict_, and would escalate every round on a single-owner repo. Rejected: **a config knob for "can this identity review"** — it is discoverable from the failure itself, and a second source of truth about identity would drift. This is deliberately **not** the same thing as the `needs human` escalation on **branch protection**, which is a policy stance about who may approve; the refusal here is mechanical and says nothing about the verdict's substance.
- **Feedback is a conversational argument, not a mechanism** — `work-implement 42, change X`. You are in the loop typing it, so there is no trust filter, no thread-resolution ledger, no auto-detect. (Code review still happens on the GitHub PR; CI / chat are equally valid revision channels.)
- **Linear repo scope = a stable label** (`work.labels.repo`), the single source of truth read by `work` (to filter) and `issue` (to tag). Projects are unsuitable — they are completable. On Linear the schema requires the key: `false` is a deliberate single-repo opt-out (the drain proceeds), while an absent key is a config error — never a licence to reach into another repo.
- **One tracker per repo**, never both. If labels mirror GitHub↔Linear, that is the integration's job; the agent writes only the configured side.

## Deferred (v2)

- **Stacked branches for dependent issues (`worktree` mode)** — branch-off-parent, PR base retargeting and a revision cascade fight the stateless model. What `worktree` does instead is **decline to select** a dependent whose prerequisite has not landed (above), which needs none of that machinery: it waits for the prerequisite rather than building on it. Ordering, the other half, is implemented for `branch:<name>`, where accumulation makes it pure ordering.
- **`branch` extensions** — `dev`/named-branch grammar is designed in (`branch:<name>`); richer targets later.
- **Structured PR-feedback ingestion** (thread resolution, author trust, auto-detect) — only if conversational feedback proves insufficient.

(The tag side of repo scope — the `issue` skill pinning `work.labels.repo` on Linear create — is implemented, not deferred.)
