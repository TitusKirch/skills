The 2026-10-12 evaluation selected Playwright with TypeScript for reproducible browser UI capture. [ADR-0039](/adr/0039-choose-playwright-for-browser-capture) records the choice and ownership boundaries. This page preserves the measurements that informed it; it does not provide a capture skill or an application specification.

## Consumer evidence

Local captures of `duxt/apps/www` at `/getting-started` succeeded at desktop 1440 × 1000 and mobile 390 × 844. The [consumer report](https://github.com/TitusKirch/skills/blob/dev/docs/_assets/gui-capture-evaluation/consumer-capture.json) recorded loaded fonts, light theme, no horizontal overflow, no broken images and no captured errors. Two desktop PNGs were byte-identical after hiding `#nuxt-devtools-container`; their common SHA-256 was `0778a7b7720029479bf356370db7cffa5ce0177f094e50159101dc63c65062aa`. This was initial consumer feasibility evidence, separate from the controlled driver comparison. It was not a committed production capture workflow, and its PNG binaries are not retained here.

## Controlled comparison

The benchmark used a frozen HTTP recording of the hydrated real Duxt development page at base commit `e15cdc436d248e10011e44b2770207b8ceaf39e2`. Replay ran on loopback inside a network-isolated Docker container. Every driver used Google Chrome for Testing 153.0.8010.12, Debian 13.6, four allocated CPUs, 1 GiB shared memory, viewport 1440 × 1000, DPR 1, UTC, `en-GB`, light theme and reduced motion. The [report](https://github.com/TitusKirch/skills/blob/dev/docs/_assets/gui-capture-evaluation/report.json) owns the exact environment, versions, statistics and caveats.

| Driver          | Evaluated version | Fresh process median (8 each) | Fresh process range | Same ready page PNG median (24 each) |
| :-------------- | :---------------- | ----------------------------: | :------------------ | -----------------------------------: |
| Playwright core | 1.64.0            |                        5.56 s | 4.52–8.35 s         |                                91 ms |
| Puppeteer core  | 25.13.0           |                        5.62 s | 4.60–7.08 s         |                                79 ms |
| chromiumoxide   | 0.9.1             |                        5.35 s | 4.75–9.04 s         |                                73 ms |
| headless_chrome | 1.0.22            |                        7.22 s | 5.76–8.43 s         |                               179 ms |

Node 24.15.0 ran the JavaScript drivers; Rust 1.96.0 built optimized release drivers. The benchmark used a custom common Debian container and the same supplied Chrome executable to control browser differences. The chosen production workflow instead uses a version-matched Playwright browser image; that image was not benchmarked here.

**Fresh process** included the driver process, a new browser process/profile, navigation, readiness, PNG writing and shutdown, plus `docker exec` overhead. Container startup and server builds were excluded. Eight rounds used a deterministically shuffled driver order (seed 286), after one two-capture warmup per driver. Fresh process/profile did not mean flushed operating-system or server caches.

**Same ready page** attached every client over CDP to one already-rendered page in one Chromium process. Three shuffled rounds took ten screenshots per driver, discarded the first two per batch, and measured the remaining 24 API calls. Connection, navigation, browser startup and filesystem writes were outside those screenshot timers. Driver-specific screenshot helpers remained inside them.

**Warm fresh tabs** were a secondary, noisy series: three new-browser batches per driver, five tabs per batch, discarding the first capture and retaining twelve per driver. Median tab creation → ready UI → PNG writing was 6.90/3.53/6.50/6.71 seconds in table order. Those batches ran at different times from the fresh-process batches. They do not demonstrate that browser reuse was slower or faster; page-load variance and workstation load prevent that comparison.

The common readiness expression required Nuxt hydration to finish and the visible `Introduction` heading to exist, then waited for fonts, image decoding and two animation frames. It disabled animations, transitions and caret visibility, hid Nuxt devtools and reset scroll. It rejected unexpected viewport/DPR, dark theme, horizontal overflow or broken images. This explicit application state check prevented a successful PNG API call from masquerading as a completed UI.

## Image validation and exclusions

All **220 controlled PNGs** passed PNG signature and 1440 × 1000 dimension checks: 8 warmup, 32 fresh-process, 60 warm-tab and 120 shared-page images, including samples discarded from timing statistics. Compared with the first Playwright warmup PNG, 76 were byte- and pixel-identical; the largest difference was 30 pixels out of 1,440,000 (0.002083%), in edge pixels. [Per-image hashes and pixel deltas](https://github.com/TitusKirch/skills/blob/dev/docs/_assets/gui-capture-evaluation/image-checks.json) preserve the comparisons. This is evidence for these captures, not a universal tolerance for future visual assertions.

The controlled report recorded no failed capture attempts. Earlier live-server exploration was excluded because concurrent source edits caused rebuilds and dynamic-module import failures. [Two recorded hydration timeouts](https://github.com/TitusKirch/skills/blob/dev/docs/_assets/gui-capture-evaluation/excluded-live-failures.json) occurred in Rust-driver attempts, but no driver-specific cause was established. Missing responses in an invalid replay preflight were also excluded. Neither series belongs in the controlled timing or failure count.

CPU and I/O load on the workstation were shared. Default launch flags and native navigation methods differed across libraries even though the browser, page state and PNG target matched. Replay applied deterministic cache headers and served recorded responses; it measured these automation adapters and rendering, not production network/server performance or Node versus Rust in general. The small sample counts, overlapping fresh-process ranges and noisy warm tabs make a broad speed ranking unjustified.

One-time setup was recorded as 6.15 seconds for JavaScript installation, 22.89 seconds for Cargo fetching, 436.37 seconds for the combined initial release build of both Rust crates and 43.08 seconds for the Docker image build. Existing package/source caches were partly reused, so these were environment observations rather than a clean-cache installation comparison.

## Evidence and reconstruction

The retained evidence is inert data, outside skill folders and `test/`. Links below open committed repository files; these JSON records are not public image media:

- [Fresh-process and warm-tab raw records](https://github.com/TitusKirch/skills/blob/dev/docs/_assets/gui-capture-evaluation/raw.json), including state, byte counts and timing boundaries.
- [Shared-page raw records](https://github.com/TitusKirch/skills/blob/dev/docs/_assets/gui-capture-evaluation/shared-raw.json), including the samples discarded before aggregation.
- [Historical source snapshot](https://github.com/TitusKirch/skills/blob/dev/docs/_assets/gui-capture-evaluation/source-snapshot.json): exact source text and SHA-256 for adapters, readiness, HAR recording/replay, held-browser setup, benchmark/analysis commands, Dockerfile and JavaScript/Rust manifests and locks. Text entries are not executable files or an installable application spec.
- [Provenance](https://github.com/TitusKirch/skills/blob/dev/docs/_assets/gui-capture-evaluation/provenance.json): original evidence hashes, omitted fixture identity and the validation performed when retaining these records. Original byte hashes identify the files before formatting; canonical JSON hashes permit validation after formatting, while embedded source hashes identify exact UTF-8 source text. Paths inside historical reports describe the original benchmark directory; the links on this page locate their retained equivalents.

The full HTTP fixture, PNGs, browser binaries, compiled Rust binaries and complete exploratory logs were omitted. The HAR was 31,232,458 bytes, SHA-256 `90029f029114bd88eea3dded0b65025ad51149f65de4db3739cd20361f729c79`. **The exact original replay cannot be rerun from this repository alone.** Raw statistics can be recalculated here, and the adapters can be reconstructed from the source snapshot. A new recording is a new fixture and yields a new measurement; a matching source commit alone does not recreate the original concurrently edited development-server state.

To reconstruct the benchmark in a disposable development directory, extract snapshot entries at their recorded paths, verify each text hash, use the recorded toolchain and locked dependencies (`pnpm install --frozen-lockfile`, `cargo build --release --locked`), and build the recorded Dockerfile. The historical image identity in the report is authoritative for that run: rebuilding its Dockerfile with unpinned apt repositories does not promise the same image. Mount the directory at `/bench`, Node at `/node` and the Chrome distribution at `/browser`; use a container named `gui-capture-benchmark-286` with `--network none`, four CPUs and 1 GiB shared memory. Start `replay.mjs` with the original hash-verified `duxt.har`, then `run.py`; start `js/hold.mjs` before `run_shared.py`, then run `analyze.py` with Pillow available. The runners expect `/tmp/gui-capture-benchmark` on the host. This description does not supply the omitted fixture or binary prerequisites. Clear prior `results/` for a fresh run, because the historical runners resume existing records.

## Why the workflow choice followed features

Playwright supplies [actionability checks and retrying assertions](https://playwright.dev/docs/actionability), [failure trace retention](https://playwright.dev/docs/trace-viewer), [configurable browser context](https://playwright.dev/docs/test-use-options) and [optional visual comparisons](https://playwright.dev/docs/test-snapshots). Its [Docker documentation](https://playwright.dev/docs/docker) requires matching project and browser-image versions. These primary sources support the workflow rationale; trace retention, other browser engines and image-diff assertions were not benchmarked.

[Puppeteer locators](https://pptr.dev/guides/page-interactions) also wait for element state. [chromiumoxide](https://docs.rs/chromiumoxide/0.9.1/chromiumoxide/) and [headless_chrome](https://github.com/rust-headless-chrome/rust-headless-chrome) provide Rust browser-control APIs. Their successful captures show that they were viable alternatives. The selected first workflow remains application-owned TypeScript spec → explicit readiness → verified PNG, with trace on failure; implementing the sibling skill and proving that complete workflow are follow-up work.
